# V1.2 CGCS2000 到 WGS 84 的转换

状态：已实现（运行时 gf-dem-tool 3）。本文说明 CGCS2000 数据为什么不再需要 `acceptBallparkTransform`，用的是什么转换、精度怎么来的，以及北京 54 / 西安 80 的处理。

## 1. 问题

PROJ 9.7.1 的 `proj.db` 里，CGCS2000（EPSG 基准 1043）到 WGS 84 只有 “Ballpark geographic offset”：不做基准转换，精度未声明。T12.1 按“近似变换默认失败”处理，于是国内最常见的 CGCS2000 数据（4490、4491–4554 各 3°/6° 高斯-克吕格）都要用户手动接受近似变换。这既不方便，也说不清结果的精度。

## 2. 采用的转换

对基准是 CGCS2000 的源坐标系（按基准 ID `EPSG:1043` 识别；没有 ID 的 WKT 按基准名 `China 2000` 识别），gf-dem-tool 把它包成一个 BoundCRS：

- 名称：`CGCS2000 to WGS 84 (GeoForge, null geocentric translation)`，标识 `GEOFORGE:CGCS2000_TO_WGS84_NULL`
- 方法：EPSG:9603 Geocentric translations，三个平移量都是 0
- 声明精度：1 m
- 不用格网，不联网，不改 `proj.db`；定义在 `tools/terrain-runtime/gf-dem-crs.cpp`

投影坐标系先严格反算到 CGCS2000 经纬度，再经上面的操作到 WGS 84。选中的操作照旧用 `-ct` 钉死（normalize 路线），direct 路线照旧由采样门槛兜底。CGCS2000 椭球与 WGS 84 椭球只差扁率（1/298.257222101 与 1/298.257223563），同一地心坐标换算出的纬度差约 1e-11 弧度，不到 0.1 mm（按扁率差估算），所以 PROJ 把这一步化简掉，生成的管线和原来的近似操作在数值上相同。区别在于：这是一个有名字、有方法、有精度声明、写进报告的转换，而不是 PROJ 默认的“不知道精度”。

报告 `crs.transform` 里会出现：

```json
"ballpark": false,
"accuracyM": 1.0,
"datumShift": {
  "name": "cgcs2000-null-geocentric-translation",
  "method": "EPSG:9603 Geocentric translations，三个平移量均为 0；…",
  "definedBy": "GeoForge",
  "accuracyM": 1.0,
  "basis": "…"
}
```

## 3. 精度依据

1. CGCS2000 的参考框架 CTRF2000 定义为 ITRF97、参考历元 2000.0，相对 ITRF97 的平移、尺度、旋转及其速率都为 0。来源：国家测绘地理信息局，“China Terrestrial Reference Frame 2000”，北斗官网 http://en.beidou.gov.cn/SYSTEMS/Officialdocument/201912/P020191202321857207749.pdf
2. WGS 84 的近期实现与 ITRF 在每个分量上对齐到约 1 cm，WGS 84 到 ITRF 的七参数按设计全为 0。WGS 84 (G2139) 对齐 ITRF2014，EPSG:9757 声明精度 0.01 m。来源：NGA Geomatics WGS 84 页面 https://earth-info.nga.mil/GandG/wgs84/index.html；EPSG:9757 https://epsg.org/transformation_9757/WGS-84-G2139-to-ITRF2014-1.html
3. 所以两者的差异主要来自历元：CGCS2000 坐标固定在 2000.0，WGS 84 坐标随板块运动变化。中国大陆板块运动速度约 3.5 cm/a，20 年的历元归算改正约 70 cm。来源：《我国常用地心坐标系的现状与发展》，全球定位系统，doi:10.12265/j.gnss.2021082701
4. 按 3.5 cm/a 推算，2000.0 到 2026 年约 0.9 m（本文推算，不是实测）。声明精度取 1 m，是对这个量级的上取整，不是统计意义上的置信区间；西部或构造活跃地区可能更大（同一来源指出速度场模型在西部较差）。

不选时间相关的 ITRF Helmert 加速度场的原因：需要知道 DEM 的观测历元和国家速度场模型（CPM-CGCS2000 等），这两样在一般 DEM 里都没有，运行时也不带。对地形瓦片来说，1 m 级的水平偏差远小于常用层级的格距（`maxDepth=15` 时 CTB 格距约 9.5 m：瓦片高 180°/2^15，除以 64，按 1° 约 111 km 计算）。需要厘米级配准的场景应由用户先在专业软件里转好，再按 WGS 84 输入。

## 4. 北京 54 / 西安 80

保持不变：`proj.db` 里只有近似操作（北京 54 的 15 m 正式变换只适用于珠江口），仍然必须设置 `acceptBallparkTransform=true`，否则报 `TERRAIN_TRANSFORM_LOW_ACCURACY`。

为以后留的选项设计（本 PR 未实现）：

```json
"preprocess": {
  "datumShift": {
    "method": "coordinate-frame",
    "toWgs84": [dx, dy, dz, rx, ry, rz, ds],
    "accuracyM": 5.0,
    "source": "某省测绘院 2019 年公布参数"
  }
}
```

- 参数含义与单位同 EPSG:9607（m、角秒、ppm），另提供 `position-vector`（EPSG:9606）以免旋转符号搞反。
- 实现方式与 CGCS2000 相同：用这些参数建 BoundCRS，选中后不再是 ballpark。
- `accuracyM` 和 `source` 必填，原样写进报告；GeoForge 不判断参数对不对，只负责可追溯。
- 七参数通常只在一个省或一个工程区内有效，桌面端要把这点写在输入框旁边。

## 5. 验证（LM，Windows，运行时 runtime-cgcs，2026-10-15）

- `gf-dem-tool crs`：4490、4547、4498（6° 第 20 带）、4554 都选中 GeoForge 操作，`ballpark=false`、精度 1 m；2436（北京 54）、2383（西安 80）仍是 ballpark；4326 不受影响。
- D1（EPSG:4547），不设 `acceptBallparkTransform`，`maxDepth=15`：

| 指标 | direct | normalize |
| --- | --- | --- |
| 耗时 | 22.6 s | 4.3 s |
| 瓦片 | 1866 | 1866 |
| 输出字节 | 625,799 | 676,620 |
| 采样点 | 1852 | 1121 |
| RMSE | 0.113 m | 0.117 m |
| P95 | 0.195 m | 0.186 m |
| 最大误差 | 0.250 m | 0.231 m |

  范围 [113.8957, 30.4500, 114.1043, 30.6304] 与 T12.1 用近似操作时一致，说明位置结果没变，只是转换变成显式、可审计的了。normalize 一列仍用 400 m 常数填外框（外框的正式处理见 `05-v12-nodata-footprint.md`）。这里的误差是瓦片与源 DEM 的对照，衡量的是切片质量，**不衡量 CGCS2000 与 WGS 84 的实际偏差**；后者没有控制点数据，未验证。
- CRS 测试集（`maxDepth=13`，换标签样本）：4490 RMSE 1.142 m（normalize）；4549 0.464 m、4498 0.458 m、4554 0.459 m（direct）；均不需要接受近似变换。
- 北京 54、西安 80 不设接受：都报 `TERRAIN_TRANSFORM_LOW_ACCURACY`，无输出、无临时目录残留。
