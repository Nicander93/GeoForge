# V1.4 T14.2 性能测量与补丁集锁定

所有数字都在 LM 上测（Windows 11，Intel 20 逻辑核，32 GiB 内存，开始时可用约 16.7 GiB），release 版 processor.exe，运行时 `D:\work\terrain-v1\runtime-v16`（master 的半像元补丁，清单带补丁集哈希）。测量时 LM 上没有其他构建或测试在跑。原始数据：`docs/terrain/v1/measurements/v14-perf-bench.json`，脚本：`tools/terrain-bench/v14_perf_bench.py`。

## 1. 补丁集锁定

- 处理器编译时内置 CTB 补丁清单（目前只有 `ctb-half-cell.patch`）。每个补丁取 LF 换行后的 SHA-256，再对按应用顺序排列的 `名字:哈希\n` 取一次 SHA-256，得到补丁集哈希（当前 `b0ed3da9d0d3f684ef75b90984711c2150fe1b300f06918accca168d4d917b6f`）。
- `build-terrain-runtime.ps1` 用同一规则算出哈希，写进清单的 `ctbPatchHashes` 和 `ctbPatchSetSha256`（原来的 `ctbPatches` 名字列表保留）。
- 运行时兼容检查：补丁名字、顺序、单个哈希、整体哈希任一不一致，运行时判为不可用，提示“请用当前 build-terrain-runtime.ps1 重新构建地形运行时”。旧运行时（如 runtime-v12c，只有名字没有哈希）已实测被拒，runtime-v16 实测可用。
- 能力输出（capabilities）增加 `ctbPatchSetSha256`。
- 断点续跑检查：任务指纹加入 `ctbPatchSetSha256`，换了补丁集的运行时不会接着旧的半成品切。
- 单元测试：补丁名字/顺序/内容不一致都被拒；哈希不受换行影响并和构建脚本规则一致；构建脚本里的 `$CtbPatches` 和处理器内置清单完全一致。

## 3. 和 P0 基线对比

- M：P0 `CTB -g 0.25` 约 12.76 s。现在 auto 下 CTB 阶段 6.96 s，单线程 28.84 s。8 线程比 P0 快约 45%。
- D4：P0 overview 21.5 s + 切片 84.1 s。现在 overview 约 17.1 s（更快），CTB 阶段 122.8–147.1 s，**比 P0 慢 46%–75%**。这次没有查原因。可能是 P0 和现在的切片参数不同（现在 maxDepth 15、半像元补丁、带校验用的输出），也可能是 CTB 本身扩展性差：4 线程以上几乎不再变快（4 线程 122.8 s，8 线程 126.5 s，平均只用到约 2.7 核）。需要另外排查，本 PR 不改。
- 线程数：M 从 1 到 8 线程基本线性变快（36.4 → 13.4 s），内存随线程数增长（397 → 1779 MiB）。D4 在 4 线程处饱和。
- 4 GiB 内存预算：整个进程树峰值约 2.2 GiB，没有超出预算，结果和 auto 一样。预算这次没有真正起到限制作用。
